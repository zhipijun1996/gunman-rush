# Godot 反冲关卡设计

## 适用任务

围绕玩家观察、射击、位移、落点和下一步机会设计。先完成区域编排，再制作房间；以真实游戏运行及专业审看收束。项目圣经与对象规范持有现行规则，本 skill 提供制作方法；项目路径、示例和行为线索须在目标版本核实。

按任务加载：

- 做整区、房间分工或节奏调整：读 [区域编排](references/region-planning.md)。
- 做具体房间、机关或布怪：读 [房间与遭遇](references/room-and-enemies.md)。
- 目标是风铃平原：再读 [平原应用](references/windchime-plains.md) 和项目现行平原 Bible。
- 实现、验证和交付：读 [交付检查](references/delivery-checks.md)。

只加载当前阶段及直接依赖；按需引用项目规则。用户只要求规范或规划时，完成对应交付。用户要求生成完整区域时，持续完成其范围内的房间与串联验证；代表样房只是校准环节。

## 操作

### 1. 确认当前真实输入

读仓库 `AGENTS.md`、当前工作线与模块导航，核对分支、未提交改动、实际运行入口和引擎版本。以本次用户指令确定范围；按项目现行权威关系读取世界、区域、动作、敌人及状态规则。核实文档所称“已接入/未接入”是否与真实消费者一致。

在 gunman-rush 中，从以下入口定位，路径变化时按索引找到现行对应物：

| 内容 | 入口 |
| --- | --- |
| 拓扑/资格/身份 | `docs/data/world/README.md` → `config/world/world.json` |
| 尺寸/门台/场景/镜头意图 | `config/world/construction.json`；场景拥有实地形和真实放置 |
| 按房读取 | `python3 tools/world/room_context.py <room_id> --contract` |
| 现行设计 | `docs/bible/room_authoring.md`、目标区域 Bible、相关对象规范 |
| 正式装载 | `FixedWorldApp`、`FixedWorldProvider`、`FixedWorldRoom` |
| 手工房间 | `game/world/regions/<region>/rooms/` |
| 动作/状态/验证 | `docs/project/module_map.md` 中对应行 |

整区任务先提取目标区域全部房号、分区、连接、能力阶段、目标与引用的摘要；逐房实现时只读本房、直接邻接和相关对象。使用当前源确定房间数量，沿用稳定身份。历史导入包、实验 runner 和旧随机 Provider 仅在明确相关时参考。

若本次明确采用新世界输入，先按项目流程合并其来源和身份关系，再施工；普通内容任务沿用现行拓扑。尺寸可按动作需要校准，并同步真实门台与地图接缝。遵循统一镜头和跨房入场规则。

### 2. 编排整个区域

按 [区域编排](references/region-planning.md) 建一份全区职责表，覆盖每个目标房和不同来向。结合主线、支路、枢纽、休息、Boss、奖励、地标与能力回访安排学习和压力起伏。沿首访主线标出必经的反冲学习与运用节点，使核心动作贯穿推进；不能只在可选支路或孤立教学房出现。

为相邻房间安排不同的主要体验；让子区域在空间关系、遭遇方式和地标上有辨识度。根据实际路线判断重复，允许有目的的练习与回访。使用轻战斗、探索、观察和舒缓连接挑战，不把全部房间都做成多拍连跳。

### 3. 将职责落实为可玩的动作和遭遇

每房使用一个精简合同：用途与来向能力、动作命题及后续局面、敌人职责、压力、允许解法、失误去向、出口/奖励/状态引用。沿用已有房间数据，不再复制一份世界模型。

声明承担反冲通行的环节，用实际地形或机关让反冲承担推进；接受不同的合理反冲解法。普通战斗允许站射、走位或绕行，反冲通过换边、后撤、制高点和命中续枪提供价值。

在普通穿越、宽落点与探索通道中主动考虑敌人。复杂连续障碍段优先保证动作可读与恢复；按 [房间与遭遇](references/room-and-enemies.md) 安排威胁，不按面积或统一配额填怪。对空白段说明观察、辨路、休息或叙事用途；无用途则缩短或设计有效互动。

### 4. 按真实能力实现

实测当前合法能力、身体包络、射击资源、冷却、普通跳及反冲范围。枚举低层、梁顶、移动台端点、敌人附近与来向入口；用这些状态校准跨距、高差、净空和恢复。

由现行输入/控制器执行动作，表现读取已接受事件。沿用项目敌人、机关、奖励和保存所有者。需要新增区域机制时先定义可观察规则、状态和恢复，做最小机制验证后再使用。根据实际配置维护参数。

并行时按房间或连接簇隔离写集，指定施工总表、共用接口和规则的单写者。先把代表房接进正式装载与相邻房，再按职责表完成剩余内容，每批都保留可运行的连通路线。

玩法确定碰撞、落点、入口和视野；已有 `godot-room-art` 可负责同风格素材、层次和拼装。将这些约束交给美术，不以美术缩放、装饰或镜头变化替代动作验证。

## 验证与交付

执行 [交付检查](references/delivery-checks.md)：必要的结构检查、真实动作与局部反例、死亡/清怪/休息后的恢复、正式入口的跨房路线，以及正常速度与镜头下的体验审看。

分别写技术结果、专业判断、用户反馈和目标设备结果；根据本次授权判断完成条件。发现缺口时修改对应设计或实现。避免把脚本条数、地图可达或三个样房通过当作完整区域质量。

长期规则直接更新现行正文；数值留实际配置；进度留任务表与一份当前交接。将临时日志、录屏和报告放 `build/` 或构建产物，只保留必要回放与持久来源。

交付当前范围的完整成果、覆盖清单、短原生录像和可运行入口。授权范围为整区实现时，继续到所有目标房被逐项处理并完成串联验证；只在实际阻断上报告明确缺件和可恢复工作。
