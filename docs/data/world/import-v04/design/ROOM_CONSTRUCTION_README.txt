逐房结构灰盒合同｜v04

一、用途与权威
world-room-layout-v04.json 是房间身份、连接、分区可达、永久动作和奖励的权威数据。
design/room-graybox-contracts-v04.json 是本批灰盒的场景接口、空间工作值、镜头意图、区域压力和交互占位合同。
design/world-graybox-bible-v02.txt（或交接包提供的同名核心规则）规定操作、跨房、地形伤害、Q、休息与修钟规则；v02为当前有效规则。
qa/room-contract-audit-v04.json 检查引用和结构，不证明跳跃、碰撞、Boss或镜头已经实机通过。

二、每个房间已经给出的施工信息
1. 唯一房号、区域、工作名、用途、职责与拟定Godot场景路径。
2. world_geometry.bounds_world_units：以当前玩家尺度为基础的可调整世界单位外框。
3. outline_candidate_local：地图轮廓缩放得到的简化形态参考，不是已验收的场景边界。world_geometry.required_reserved_areas逐项给出门内通行带、左右门连续地面、入口运动包络、安全台及其净空、Boss竞技区，实际可用包络必须包含这些矩形。
4. sections / internal_routes：入口预览、主体和必要支路分区，房内环境能力要求及对应的交互/出口。
5. doors / entry_spawns：成对门朝向、出入模式、目标分区、门洞和入口台工作坐标。
6. camera：四类镜头之一，入口、主体、转角/楼层和战斗构图意图。
7. difficulty：普通通路C/T上限，可选峰值和Boss峰值分开。服务房C0/T0不等于所有带休息点的房间都没有挑战。
8. first_visit：Boss的原始最低战斗资格、局部主体通路条件、A/B/C实际模拟首访配置及推荐攻击区间。推荐攻击值不作为门槛；首访样本不冒充所有可能路线的最小证明。
9. 永久奖励、NPC、库存、修钟、捷径、休息与裂缝的唯一交互引用和所在分区。
10. terrain_failure：普通1HP、特殊2HP、按来向返回挑战入口；归零走死亡，不隐式回血或刷新周期。

三、尺寸与镜头怎样使用
全部房间现在都有明确的施工工作外框，但它们仍可以因样房结果调整。
世界图坐标不按一个统一倍率复制成游戏像素。普通镜头1.60只用于比较/估算，对应1280×720视口下800×450世界单位；正式普通镜头值在首批样房中确定。
工程先从仓库当前控制器读取真实参数，保持玩家跑速、跳跃、反冲与碰撞体；不要为单房把角色调快或跳高。
外轮廓、可走地形、战斗区和相机区是不同数据。结构阶段先给外框、接口、入口台、主要高差和能力挑战占位，内部精密平台与敌人细节在后续制作。
严禁自动把outline_candidate_local封闭成碰撞围墙。部分门和安全台处于该视觉候选多边形外，但已在工作外框内明确预留；施工时必须扩展或重画本房可用轮廓，并用真实内部前廊接入所属分区。
required_reserved_areas内collision_intent分别说明“真实实地”和“应留净空”，不能把所有矩形统一填实。门外半边由目标房的成对入口预留承担。前廊不能用瞬移代替，也不能直连主体从而绕过入口能力障碍。
合同审计检查所有预留矩形均在outer bounds内，并检查Boss门口/入口台/入场动作包络与竞技矩形无面积重叠；这只是几何占位一致，不代表真实跳跃、走廊、镜头已通过。
F-R04空心树干采用624×1616世界单位工作外框，明确是纵向房；原来近正方形的屏数换算已不作为施工依据。
22场Boss采用各自招式类型的工作竞技区，入口前庭与战后奖励区另留；不再把20场Boss统一套成同一场地尺寸。
Boss竞技尺寸保持各场独立，外框另增加左右各320、上下各288世界单位前庭工作边带。入口安全台和动作包络在战斗矩形外，玩家实际经过前廊触发线后才开战；具体前廊随该房地形校准。
镜头前瞻基于实际移动趋势和房间构图目标，不跟随枪口/鼠标。多边形房以多个相机区控制，不用外接矩形包办。

四、门接口的空间解释
普通门只有左右步行、向上自动侧台落地、向下安全台三种跨房行为；裂缝等交通单独由交互触发。
每对门接口朝向相反。旧地图有69对弯折/错层候选端点需要归一，逐项记录在door-coordinate-audit-v04.json。
connector_owner_room 表示需要在这间房增加短转角/楼层接续廊，把图上的接入方向接到实际门。该接续是真实空间和镜头过渡，不是额外瞬移。
C30暗渠A保留前后深度配对通道的地图例外标记；它仍采用步行入口，不因地图距离自动新增房间或岔路。
所有入口安全台必须留在其绑定分区，自动跳台不能替玩家越过该房的能力阻隔。

五、能力路线与事件
普通物理门不读取H/W/D/Q，门可有真正的道具、剧情、机关条件。
internal_routes.requires 用于规划和模拟。游戏中由索点、墙面、高差、断桥和相位光幕实现，不生成看不见的能力检查墙。
玩家必须进入交互绑定的分区，才能取得奖励、开捷径、修钟或触发Boss。仅进入入口预览区不能触发房间深处内容。
单个action_id只实例化一个物体；shortcut_operators等是同一个交互的其他视图，不能复制第二个按钮。
2秒只限制Q保护，普通射击和普通反冲保持原节奏。Q只处理怪物/普通敌方攻击和光幕；荆棘、齿轮、熔岩、毒水仍照常伤害。
真正落地恢复Q资格，换房、交通、地形复位不清冷却。连续Q路径要有真实落脚和足够时间或安全等待位。

六、何时可以铺开全世界
结构开发可以从本版开始：场景名册、共用房间基础场景、门/入口台、分区、主要能力阻隔占位、NPC/Boss/奖励/修钟交互占位和永久状态均有接口。
首批需要完成共用运行时校准：教程与小站、H树干、Q光幕、普通/大型Boss场、上下跨房。它们是第一批开发任务，不要求先把216间内装设计完。
验证后可并行铺216间结构，内部挑战、美术、NPC对白、装备效果和Boss完整招式按房间逐步完善。
Shop的精确金币价格、全部装备效果、最终BossHP不是世界拓扑开工门槛；占位必须保留唯一ID与正确取得位置，不能假装已完成经济/战斗平衡。
不能以这份合同声称所有跳跃、门台、镜头或Boss已经可以游玩；物理可行和可读性仍由实机验收。

七、复现
在完整交接包中运行：
python design/build_room_contracts_v04.py
脚本读取根目录canonical、source_inputs内v03基线与simulation/route-replays-v04.json，输出逐房合同、接口审计与区域难度表。
canonical或回放更新后应重新运行，保持canonical_sha256与所有派生文件一致。
