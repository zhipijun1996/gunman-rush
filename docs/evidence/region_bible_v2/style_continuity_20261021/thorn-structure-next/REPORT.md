# 两张实机重看后的结构决定（仅预制作）

**结论：不再开一轮“宿主内画几根编织藤”的覆材试做。** 它仍是已STOP木肩/棕色条带的同类，即使改覆盖范围、交叉次数、名字也不构成新方向。native2已经满足有限静态“刺生于真实平台”的审查；后续优先问题是平台本身的形，而非再给这两条已成立的边缘加细节。以下只给一个真正改变实体轮廓的有限G0候选与工程障碍，不实施、不签通过。若根任务要求“碰撞不变且低成本解决有机大形”，当前结论是NO-GO。

## 实际看了什么

重新打开native2原始1280×720 HUD两图、用户参考原图、八实体G0实际prototype，并读native2/木肩/G0独审。native2 map1 camera[755,180]/pose[755,260]；map2[675,180]/pose[675,260]。它们的版本/Manifest分别为v15/3a49ca…f00与v15/359f58…85e。完整路径与SHA在proposal.json，不拿当前源重算旧通过。

两图里藤干与白刺确实已贴宿主；上方约660屏幕像素宽的深色横体、下方大块实体及一批细绿单向台仍主导整体。map2的真实90wu下折与40wu上折已由native2弯根连接；map1用平直真表面连接。它们不再有需要“假根补接”的空隙。用户参考的重要关系是实体自身已经是弯曲/束生的枝体，藤与尖刺沿该体量生长，不是把更多纹线贴到一个方箱上。

木肩独审明确拒绝的是“nested/parallel folded brown ribbons applied onto the existing dark rectangle”。因此“扩大到整个宿主、加两根交叉内藤、给它叫编织体”仍不能当新G0。放大TREE用背景补树体已NO-GO；八矩形删下腹实际产生粗剪阶，且使原native2下弯根guard失效，已RETHINK_STOP。均保留，不改密度/颜色/阶数/透明度重试。

## 真正不同的联合构造：先让一块实体自身长成弓背枝

若后续允许一个设计G0，选map2上方`hollow__belly_roof_upper`，保持原[380,80,390,90]实体原件，**向其顶面增加一块实际凸多边形弓背实体**，不是继续削下腹，不增加八块阶梯，不用背景补支撑。cap九点按顺序为[380,80]→[416,60]→[464,40]→[520,28]→[576,24]→[632,28]→[688,40]→[736,60]→[770,80]。闭合边是原y80顶面，新增实体全部在y24..80。加料是有意空间变化；原平台及所有危险矩形不静默变形。

这只是一个弓背带刺枝的轮廓研究，不是整棵巨树：保留两端连接与下方原危险面，顶面成为可触碰的弯背，体内才组织两束互相咬合的木藤。藤体有真实体量承载，端部的木纤维与既有刺根连续；不会靠细线声称厚根。它不会自动解释整图根基、竖干、树洞或全区网络。原v15/旧保存不能用这个场景冒充。

为何选上方：原下方166wu的削体方向已停止；上方90wu枝的上轮廓在当前正常镜头能完整看到，新增cap抬高56wu，在zoom1.2时仅增加67.2屏幕像素的真实枝背。比把上部全部填满的背景TREE范围小。所有点来自明确的同一物理多边形，不用玩家轨迹挖alpha mask。新增多边形面积及精确顶点在JSON；它不是路线通过证据。

**这并非现有shared47 renderer可直接吃的变更。** `UnderworldTerrain.build`只接受轴对齐Rect2；把polygon只放进Physics、仍给renderer旧矩形，就是错误。把曲面拆成更多细Rect也是停止方向的参数延长，不能用来绕开这次判断。G0若做，只可用Godot内建CollisionPolygon2D/Polygon2D做这一个有限实验，不建立通用polygon生成系统。原shared47几何/材质/原始平原对照保持原件；新实验轮廓若需专门适配，必须明确标出该适配未经生产契约认可，不能声称canonical rect-union/render一致。

同族风格要求仍严格：实体内部以原Underworld原生16px/32wu簇与当前Forest母块组织；边缘native2wu整像素木藤/苔簇，少量苍白刺尖来自现有危险层。不能直接用高分辨率木纹、抗锯齿矢量描线、纯色多边形或Hollow Knight资产冒充合格母版。新cap把旧y80苔边变成体内接缝，因此必须在**整个新真实枝体**的绘画里消除该内苔线，并沿真实新上轮廓形成边缘；不能保留一条假可站面的内部绿线。当前没有完成这张native结构画，也没有完成有限轮廓适配，所以这不是ready-to-run素材包。

## 对碰撞、路线、危险的诚实影响

必须变化的是：新凸polygon真实碰撞/新上轮廓站位，以及原屋顶绕行的净空与落点。新增cap不得伪称visual-only；哪怕所有旧Rect原件还在，实际solid union已增大。现有v15注册器和fixture应拒绝该实验。若将来晋升须独立layout/version与消费者/保存重建，不直接改默认v15。

可精确保留的是：原下侧危险[380,170,390,20]仍由原roof_upper真底面170承载；右上40wu下折、右cap底210、下方90wu折与全部8段危险宿主均原样。新增cap只在y<=80，不能画刺到新增安全上表面。图内S/B/C及M/E/D/R坐标不因此移动；原中央横洞与下降洞的几何净空没有直接削减，但“没有削减净空”不等于Motor/raycast/路线已经通过。

需要重验的是：屋顶/高支路走路跳跃、任何从上向下穿过新增cap空间的身体/弹丸/H射线、恢复与反向路线，以及相机上缘HUD遮挡。旧路线Driver若假设roof top固定80，其stand/body目标和源记录会失效，不能把投影到旧v15的轨迹当新场景通过。图1原roof430wu宽，与图2并不相同，不能把同一390wu素材横向拉长后直接扩图1。

## G0预算与停止条件

最小真实G0只做**一个map2镜头的control/prototype两图**，普通App、UnderworldPlayer、HUD与原危险层保留；同camera/zoom/pose，暂停时无新增Motor步，原Stage生成Manifest原件/hash作为来源；实验实际solid含新cap、明确production_pool=false/未准入/当前scene不同。另用原map1完整图作风格/重复性只读参考，不自动给它相同新物理。应先有一张准确native结构画与内建有限polygon的源级对齐说明，再安排原生截图；本轮不做资产或脚本。

判断问题必须足够尖锐：真实新增弓背是否让这一个带刺平台首先读成有体量的枝，而非方箱上额外戴一团木料？藤的编织关系是否从实体结构读出，而非纹线拼贴？普通HUD、当前果实和中央净空是否仍是最先读到的动作信息？若仍像“方块戴帽/棕色带子”，立即STOP；不调cap高度/顶点/颜色再两轮重试，不用背景树挽救。

制作规模：一张有限native枝体画、一个内建polygon碰撞、一个有限实验绘画适配、一次两图对照，理论上可以局部G0；**绝不是现有脚本加个纹理即可，绘画适配尚未被验证为低成本。** 若需要改共享renderer、通用clip框架或生产注册才能诚实渲染，停止本G0准备，不为看一张图先推进v16。即使画面成立，生产仍须独立关卡/美术联合设计与完整路由成本评估。

最终建议：不再尝试零几何棕藤覆材；先由关卡与原生像素绘画共同确定这一真实枝体能否以有限源表达。当前只允许保留这个明确物理delta的待评候选，状态HOLD_FOR_SOURCE_AND_RENDER_FEASIBILITY；不把它算作继续开发完成、艺术通过或整区宏观补救。
