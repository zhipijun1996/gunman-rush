# 审查方法

从本任务的设计目标、真实场景与可能失败的边界形成审查范围。先读相关圣经和对象规范，再核实现、配置与证据是否表达同一件事。

## 审查顺序

1. 冻结被审源码、规格、场景、Seed／输入和参数来源，记录审查者与实际观察范围。
2. 重现目标体验，再主动尝试最便宜打法、不利资源／相位、边缘站位、中断、返回和重入。比较移除关键机制后是否仍有同样体验。
3. 行为看真实操作与伤害／奖励结果；画面看正常尺寸和连续动作；声音实际试听。结构、轨迹、截图和命令分别只能证明自己的范围。
4. 每条发现给预期、实际、位置、最小复现、影响、责任专业与回归建议；修复后核同一对象的新版本。

## 结论

使用 ACCEPT／REJECT／UNVERIFIED 并明确范围。技术、正式集成、专业视听判断、用户体验和实体设备分别记录；缺少的证据留未验证。报告使用 [审查模板](templates/review.md)，结果归当前工作线，不向长期设计追加审计时间线。
