# 开发与内容审查

普通修复、规则调整、工程和文档维护只记录当前交接及相关检查，不强制质量卡。新区域、新地图、新怪物等新内容按需用卡，重点判断美术是否统一、玩家体验是否成立。任务进度归 [任务表](tasks.md)，与审查结果分开。

## 制作与审查

1. 读相关圣经、对象规范和真实代码，明确本次范围、玩家会观察和操作什么、需要验证什么。先整理受影响的设计正文，再实现与配置。
2. 整区任务先交付真实空间总图，检查房间占地、成对门口、主支路和回环；不成立时暂停依赖这些几何的房间扩展。随后完成真实可玩的相连样板，将角色、地形、敌人、动画、声音与反馈放进实际场景。直接检查正常镜头和连续操作，修复主要缺口再扩展。
3. 美术检查尺度、画法、材质、色光、根基、动作衔接及实际合屏；体验检查可读预告、操作与反制、落点、探索决策、节奏和失败恢复，按对象取相关项。
4. 执行受影响的功能回归，保存具体来源、命令、结果及必要音画。用专业判断说明继续、返工或尚缺什么；没有观察到的内容不写通过。

用户要求快速灰盒迭代时，每轮默认只做导入、场景编解码器、基础碰撞/安全落点和受影响的少量关键动作检查，随后立即提供可试玩版本。完整路线自动通关、极端绕法、长时间恢复压力与设备专项留给定稿或用户明确要求的验收，不作为每次生成和微调的前置。基础校验通过不能写成全链体验、难度或趣味已验证。

快速视觉反馈以一间房施工、相邻房验接缝为单位，每轮同时提供整房实机总览、标明出入口／主支路及关键空间职责的整房图、正常速度短录屏和同机位对照；总览注明检查缩放，不冒充正式镜头。反馈在本房闭环后再扩展。累计2–3间确认后再统一发布运行包，需要判断操作时可提前试玩；媒体更新不要求重导出整个游戏。

结构灰盒只验真实结构、状态与可玩流程；正式内容另验美术、完整战斗与经济。真实运动、碰撞、资源、奖励和恢复等回归仍按改动选择；自动检查只证明自己的覆盖。

每次内容制作按以下六项执行；具体规则仍由对应圣经和Skill持有：

1. **唯一输入**：只读当前任务、目标房与直接依赖；按仓库AGENTS中的反馈与冲突处理规则，将用户意见写回权威正文，未决设计冲突先问用户。过时报告删除，被替代实现直接更新并清除无消费者分支，历史留Git。
2. **动作成立**：当前房间说明观察、决定、动作、结果与失败去向；以真实控制器验证声明的反冲/机关职责及相关绕行反例。
3. **空间成立**：主支路、门位、相邻接缝与回环一致；按房间制作规范检查收集路线、房内分区和路线生态，地图和实际通行共同检查。
4. **合屏成立**：按认可参考检查体量、根基、景深、光照和可感知风向；UI检查实际显示比例与触控状态。
5. **先校准再扩展**：总图成立后，相连片区的玩法与美术同时成立，再用不同几何验证方法，随后完成全部授权房间。已知的整体空间、入口安全、支撑/层次或主要体验缺陷阻止扩展；不能一边写质量失败一边继续按房数推进。已知镜头盲跳、房界悬空、无恢复坑或无用途空白时，不发布为新的可玩版本；施工版标签不豁免这些基础要求。
6. **证据对应结论**：技术、体验、视觉分别记录，缺项不写通过；实际反例推翻通过结论时立即纠正，不能为迁就实现改变标准。

这些是执行顺序与检索重点，不新增一套设计规则或用户审批。素材数量、功能存在、脚本通过和截图产出均不能自动满足内容质量。逐房审查入口应支持房号、真实来向、合法能力阶段、重置和相邻过门，隔离正式存档并显示夹具状态；它用于快速重复检查，不能替代新档学习与连续探索。重构时保留已验证的局部玩法和表现，先比较新旧同位置画面、转折视野与失败恢复；坐标通关只证明可执行，不能作为初见可读性结论。新会话或上下文恢复后，重新读取当前交接、房间制作规范和本批已发现的失败，不从摘要中的“通过”继承验收。先用本地正常镜头/控制器完成审看，再发布有明确验证目标的小批试玩，不让用户从开头反复跑图承担基础验收。

逐房试玩从标题、暂停菜单或试玩顶栏进入。网页 `?review=P-R22&entry=INTRO-P21-P22%3AP-R22&stage=base` 可直达指定来向；`stage` 可选 `base`、`h`、`hd` 和后期隔离能力组合 `hwdq`，原生入口使用同名 `--review/--entry/--stage` 参数。逐房夹具开放开场教学和小站地理通路，能力仅按所选阶段授予；Boss胜利、修钟、收集和奖励捷径仍需实际完成。重置清除本次试玩进度并保留所选起始阶段；退出后正式继续读取原存档。逐房模式的大地图显示实际源登记的连通地区，正式模式仍只显示探索过的房间；查看总图不写入探索记录。正式逐房清单以已施工合同为准；工作台额外灰盒必须在范围登记中明确列出，不能以直达夹具证明正常路线取得了能力或相邻地区已施工。

## 质量卡

机器格式由 [policy](policy.json) 描述，当前规范版本 **2**。只记录适用项：

- 新内容通常记录 visual／gameplay，分别说明美术统一与玩家体验的实际观察和证据。
- 动画、声音、性能、正式接入等按本次范围增选。未做但本次需要的检查写 unverified；不适用的项直接省略。
- 用户反馈、实体设备和额外独审仅在任务明确需要时成为完成条件。Codex专业判断、真实用户反馈和真机测量分别标明，不互相代签。

结果使用 passed／failed／unverified，并说明范围与依据。失败给出复现、影响及下一动作；缺少证据写未验，不补写虚假PASS。卡片记录内容审查，不存工作流状态。

手动自动生产可按目标选择 G0 设计、G2 视听与体验、G3 正式接入、G4 技术检查、G5 约定的用户／设备验收。它们是适用检查的名字，不是所有任务必须顺序通过的关卡；只有本任务明确要求的检查才影响对应范围的完成。

```sh
python3 tools/quality.py init --id TASK-ID --type enemy --output docs/project/worklines/<议题>/quality/record.json
python3 tools/quality.py check docs/project/worklines/<议题>/quality/record.json
python3 tools/quality.py check
```

默认 check 只读取当前工作线的卡；临时结果由该任务按需引用。check 检查记录与证据一致性，`--require-complete` 用于本次约定范围的完成声明，不代表整个游戏获用户认可。

## 验证与证据

日常使用 [Harness](harness.md) 的固定四项CI，专项从 [模块导航](module_map.md) 按实际影响选取。差异审查 `python3 tools/check_quality_diff.py --base <基线SHA>` 用于查看记录声明、素材来源和检查变化，不要求普通任务补卡或追加独审审批。

证据写清源码／版本、生产者、方法、观察及可恢复路径；命令记录退出码，音画保留实际入口与正常速度范围。JSON卡绑定文件SHA和来源，防止旧日志、错误媒体和自签用户反馈被当成通过；它不能认证审美、人的身份或设备体验。

采用 [审查模板](templates/review.md)。交付前通读修改后的完整正文，核对实现和引用，清理临时稿；将结果与恢复动作更新到唯一当前交接。
