# Codex 协作与交付

## 开始任务

从最新 `origin/main` 建主题分支／独立工作树，记录基线SHA、目标、完成条件、允许写集及依赖。接续同一任务则先核对原分支、未提交改动和依赖版本。使用 [任务模板](templates/cloud_workline.md)，只建本任务需要的工作线文件。

[任务索引](tasks.md) 每个父议题一行，内部阶段和局部质量卡留在工作线。`current_state.md` 描述当前产品事实；设计圣经、具体数据和临时文件按 [四类索引](../README.md) 读取。

功能开发先核相关圣经与对象数据，先更新设计／数据正文，再修改代码与配置，同一任务同步完成。参数只在实际配置／Definition 维护，数据规范引用字段和含义。设计未定项明确保持候选，进度和验收记录不写进对象规范。

## 多会话交接

每个任务指定一个负责人。并行会话使用不同分支／工作树；共享文件由一个写者负责，其他会话交接口需求或可审阅修改。独立审查者读取冻结版本与证据。

在任务已有 `scope.md` 或 `results.md` 维护一份当前交接：

- 目标、完成条件与本次用户授权范围。
- 基线、分支、源码SHA、未提交文件及负责人。
- 允许写集、共享接口和依赖PR／SHA。
- 已完成内容、真实检查命令／退出码／报告路径。
- 阻塞、未验证范围、下一条可执行命令。

交接直接更新字段，不追加时间线。任务结束清理中途审计／临时计划；有效规则进入当前设计／数据，必要原始证据归档，其余历史由 Git／PR 追溯。恢复先核代码、规格与证据身份；本机 `build/` 产物须有持久来源才能供另一会话复用。暂停前提交／推送可恢复工作，说明未提交项。会话不会自动共享内存或接收后续反馈。

## 验证

日常运行`python3 tools/ci.py`四项检查。开发从 [模块导航](module_map.md) 和 [Harness](harness.md) 选择相关专项，保持脚本原断言、预算和退出判定。记录具体命令、版本与实际覆盖。

质量卡和专业G0–G5方法仅在需要管理重要内容验收时使用，规范见 [开发质量](development.md)。纯工程／文档不自动扩成完整游戏、用户或设备验收。

## 交付

按评审需要选择：观察局部变化交真实Godot短片；需要操作交Web；纯工程交修改与检查结果。媒体写明源码、构建、Seed／输入和复现条件。

试玩更新优先复用目标源码已验证的Web包，通过 `deploy-prepared-playtest.yml` 发布；缺包或运行源变化时重建Web并执行受影响检查。公开后核 `build-info.json`、完整PCK身份及真实入口。大型PCK使用已有内容寻址分块渠道。

每条工作线需要独立Preview时使用独立托管目标；现有prepared工作流会替换整站。源码PR、网站更新与商店发布各按用户授权范围执行。PR面向main；合入前核Git祖先、接口、UID、导入、保存、Manifest与真实消费者。
