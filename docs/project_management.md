# 项目管理

[活跃任务](tasks.md) 只保留当前父议题、依赖、状态、下一动作和工作线入口；[归档](archive/tasks.md) 保留必要旧 ID 与证据。当前产品事实只更新 [current_state](current_state.md)，各任务在既有 scope／results 中维护一份可恢复交接，规则见 [协作交付](cloud_production.md)。

## 文档职责

按 [四类索引](project_structure.md) 维护：项目管理写状态与交接，设计圣经写方向和长期约束，具体数据写对象行为与参数来源，临时文件只服务当前调查／实验。后两种长期规范都直接整理正文，保持完整、自洽、准确，不追加修订时间线或“最新覆盖”段落。每条规则只在一个权威位置定义，其余文档引用。

## 开发顺序

1. 明确任务与真实消费者，从索引读取相关圣经、对象数据和实际 Resource／配置，核对是否存在未决设计或版本冲突。
2. 先修改受影响的设计／数据正文，写清行为、状态、表现、参数字段与验证范围；沿用已有文件。具体数值只维护于运行配置／Definition，不手抄第二套默认值。
3. 再修改代码与配置，同一任务同步实现、文档及必要来源绑定；重要决策未定时保持明确候选，不以推荐代签。
4. 运行相关现有检查，记录真实结果；交付前核文档与实际消费者相符，清理临时稿和生成物，更新当前交接与父任务一行。

内部阶段和局部质量卡留在父议题工作线。状态沿用 planned／ready／in_progress／review／blocked／awaiting-device／done；代码合入、技术验证、独审、体验与设备分别记录，归档不等于完成。

## 结束与追溯

任务结束时将有效规则并入圣经／数据正文，将当前结论和恢复动作并入结果；删除无消费者的中间审计、计划与副本。只保留验收、恢复、原始来源、许可或复现需要的证据，写明精确来源和用途。Git／PR 保存变更历史，不在项目入口维护历史任务流水。

主题分支和 PR 面向 main，保护用户改动；合并与发布按本次授权。日常 CI、专项和手动交付沿 [Harness](harness.md)，本体系不新增门禁、状态系统或自动发布流程。
