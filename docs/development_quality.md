# AI开发流程与体验验收

本流程把已有玩法、美术、输入与验收契约落实为每次交付的检查门槛；不改变玩家物理、奖励政策或正式流程。当前基线见 [项目现状](project_status.md)，新用户要求优先于历史规格。开发目标必须写为玩家获得的体验，不能只写“加了组件/贴图/按钮”。

## 一次任务的流程

1. **确认基线与问题**：fetch后比较分支和内容；记录来源ref/commit、正式入口、线上运行版本及已有局限。在 [任务模板](templates/development_task.md) 写明触发、当前结果、目标体验、受影响契约、依赖与具体复现路线。不得从旧main直接接续最新玩法任务。
2. **先写验收再实现**：分别填写功能、关卡/战斗、视觉、动作、声音/UI、性能及回归。确实无影响的维度写具体原因。每项有实际场景、失败条件和证据；将阻塞项与可独立开发项分开，不为普通可逆实现反复请示。
3. **做完整样板**：新增机制先做固定、真实可操作的一段，同时接入预警、反馈、美术、动画、失败恢复与收尾，再开放随机池。沿用当前风格锚点、已接入素材、真实Motor与资源服务；最终画风认可独立记录。占位可用于明确技术切片，保留独立表现任务；不得把占位切片宣布为完整功能体验交付。
4. **接入正式消费者**：从标题/家园正常进入能使用；练习与正式场景的开火资格、奖励、封门、存档、死亡优先分别验证。不要只测试 Lab 或直接调用函数，遗漏正式装配路径。
5. **开发者自验与修复**：针对改变运行必要测试；GUI用正常输入走相关路线，录制连续动作。暂停/恢复、取消、回退、重载、死亡和幂等按风险覆盖。保留失败日志和最小反例，不删断言或扩大碰撞余量来伪造通过。
6. **独立严格审查**：依当前 AGENTS D080–D082，每轮新独立审查方可否决；审查正式消费者、反例及实际画面，不能复述作者报告。否决先修复再复验，保留审查记录。无独立审查能力时如实标待审，不自称独立通过。
7. **交付与体验验收**：同步 tasks/acceptance/handoff，提交推送并创建PR。玩法变化按已授权流程发布已测试ref，核对线上source_commit/PCK/hash及默认入口；纯文档不重新发布游戏。真实设备、美术认可与真人趣味保持独立待验，允许技术review交付，不冒称最终完成。

## 通用质量门槛

| 维度 | 必须达到的行为 | 退回条件与证据 |
| --- | --- | --- |
| 功能/状态 | 正常入口可达；实际对象生效；取消/暂停/回退/离场无旧请求；奖励与支付只发生一次 | 只在fixture工作、正式场景漏接、死亡仍结算、回退刷资源：阻塞；自动反例+正式GUI |
| 玩法/空间 | 写出具体操作与选择；有观察区、安全落点与失败回程；敌人/机关影响实际走位；必要路线符合现有能力与精力 | 改名/镜像/数量充当新玩法，必经盲跳或无资源死局：退回；原Motor轨迹+玩家路线记录 |
| 美术/读图 | 同一合屏的角色、敌人、机关、地形、远景、UI光色/材质协调；危险、实体、单向板、可互动目标辨识一致 | 原画漂亮但运行割裂、危险被遮、透明光晕、重复硬切、贴图误导碰撞：退回；同seed前后合屏、深浅底和手机尺度 |
| 动作连续性 | 按改动覆盖相关动作链：idle→run→jump→fall→land及aim→release→recoil→recover连续；起落锚点稳定，左右/八方向瞄准不漂；hurt/death/phase转换可读 | 少量姿态存在但切换闪跳、滑步、枪口漂移、单帧截图冒充流畅：退回；正常速度与慢放连续录像 |
| 战斗/机关反馈 | 预警→动作→命中/拒绝→恢复有清晰对应；只有接受的事件发声/反馈；可看见弹道、铃芯与开门结果 | 未命中冒充命中、声音错相、反馈遮落点、动画与攻击窗口错位：退回；实际输入及事件时序 |
| 镜头/UI/输入 | 瞄准坐标正确；落点/威胁能提前看见；菜单不误射，地图不误揭雾；触控互不抢占 | 镜头突跳/遮挡、玩家出画、按钮命中区错位、关闭菜单误射：阻塞；正式GUI+设备录像 |
| 性能/生命周期 | 动效与对象数量有界，重复进入/死亡无持续增长；设备60fps目标与20分钟输入稳定性沿用A16 | 构建成功充当性能证明：退回；设备型号、分辨率、p95帧时、内存和加载记录 |
| 回归/复现 | 原物理、危险扫掠、资源/存档、版本化布局保留；新旧seed与版本边界可解释 | 放宽旧标准、删除失败、修改物理适配地图未授权：阻塞；命令/版本/退出码/日志/提交 |

动画帧数不作统一硬指标：程序动画、关键姿态或逐帧均可，但需证明动作衔接和攻击窗口清晰。主观美术与趣味由用户/真实试玩者认可，AI可以指出缺陷，不能代替认可。

## 随机生成改动的附加验收

- 先验证固定配方、接缝和正反路线；动态机关覆盖四个已有初始相位，必需反冲段保留真实射击正例与适当无枪反例。不可假设每个模块单独可过就能整段可过。
- 批量样本至少保留现有50seed×两图对照范围；扩大样本应说明目的和时间预算。分别记录整图保底与占地保底、连接/动作签名、压力覆盖和重复段；数量统计与物理可达证据分开。
- 正式第一/第二图、教学、商人/奖励、反侧捷径、单向撤离和Boss接近路径实际消费；用当前射击精力，不能免费补能或传送跨过风险。
- 收集早到Boss、探索成长、高难宝箱再返回三种路线的玩家观察：迷路/停顿原因、误读、重试位置、疲劳与资源情况。时长和重复率只作为对照，平衡阈值须在任务中声明为候选，不自行当成用户确认。
- 新局重抽、同seed同版本重放、段回退不重抽、快照重载与旧版本拒绝分别验收。随机流新增或抽样顺序改变时说明哪些内容重排。

## 状态和证据不能混写

任务沿用 planned/ready/in_progress/review/done/blocked/awaiting-device。每个交付另列分项证据结果：技术、正式GUI、视觉审查、动作审查、独立审查、设备、真人趣味，使用 passed/failed/unverified；用户认可记录日期与范围。

全部必要证据齐全才能将对应任务标 done；只通过自动/GUI时保持 review，需要真机项保持 awaiting-device。明确文档任务可在文档检查与独立内容审查完成后 done，不要求无关的玩法或设备重测。缺失证据不阻止其余独立工作，也不允许把缺失项目忽略。

证据至少包含：task、日期、source commit、运行build、场景/seed/配置、命令或设备、退出码、实际观察、失败与修正、artifact位置、未验证范围。截图证明画面，录像证明连续动作，fixture证明指定状态，均不得扩大结论。

常用验证入口：每次执行 `python3 tools/check_docs.py` 与独立 `python3 tools/check_world_design.py`；按改动选择 `python3 tools/run_tests.py`、`python3 tools/run_plains_ten_tests.py`、`python3 tools/run_plains_region_tests.py` 和相应普通浏览器脚本。运行前 `bash tools/godot.sh --version` 确认固定版本；不以旧版引擎结果替代。稳定版全套/导出门槛沿用现有发布workflow，不为低影响文档新增镜像测试。
